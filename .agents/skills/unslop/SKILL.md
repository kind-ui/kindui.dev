# Unslop

Scope is the diff (`git diff <base>...HEAD`) unless you're given files. Behavior never changes: the same checks pass before and after, and nothing public is renamed.

## What goes

**A comment that says what the next line does.** Delete it. If the line isn't clear without it, rename something.

```ts
// Open the menu when the button is pressed.
button.addEventListener("click", openMenu)
```

**A comment on every declaration.** Most constants, fields and functions need none: the name and the type say what they are. Delete each one that doesn't stop a reader from getting the code wrong.

**A comment that explains the design.** What a value holds, where it's kept, who reads it. The code says that. Keep the one fact it can't show, in a line, or delete the comment.

**A comment longer than three lines.** Cut it to the reason. A longer explanation goes in AGENTS.md, the spec, or the commit message.

**A comment that narrates history or the task.** "Now we", "Updated to", "Fixed the bug where", "Task 2", "As requested". Delete it. Git holds the history.

**A section banner.** `// ---- Helpers ----`, `/* State */`. Delete it. Split the file if it needs signposts.

**JSDoc that repeats the name.** `/** The title. */ title`. Say what the reader can't see: the default, the unit, when it's called, what happens on change.

**A hedge or a sales word in a comment or a doc.** "Robust", "seamless", "comprehensive", "simply", "just", "easily", "ensure", "leverage", "utilize", "note that", "it's important to". Cut the word; if nothing is left, cut the comment.

**A defensive check the types already rule out.** `if (!items) return` on `items: Item[]`, `?? []` on a value that's never undefined, `try` around code that can't throw. Delete it.

**A cast or `!` with no reason.** Make the type right, or say why in a comment.

**A one-caller helper, or a wrapper that only renames.** Inline it, unless its name explains something the call can't.

**A name that says nothing.** `data`, `result`, `item2`, `handle2`, `temp`, `flag`. Name what it is.

**An option nobody passes,** a parameter with one value, a config object for one setting. Delete it.

**Hand-written code a framework or CLI already provides.** A custom search dialog, layout or MDX component that Fumadocs ships, a redirect Next.js or Wrangler config can express. Replace it with the framework's.

**Logs, probes and commented-out code.** Delete them.

## What stays

- A comment that says why, in three lines at most: a browser bug and the browser, a framework quirk, a trade-off, a link to the spec section or docs page that pins the behavior.
- Code generated by `create-fumadocs-app`, `@fumadocs/cli` or `shadcn` stays as generated unless the change needs it different.
- JSDoc on every public export and option. Make it say more; don't delete it.

## Steps

1. List what you'll change, by file, before touching anything.
2. Make the changes.
3. Run `npm run lint`, `npm run typecheck` and, when you touched pages, config or content, `npm run build`. Check exit codes.
4. Delete each comment left in the diff and reread the code. If it still reads right, leave it deleted.
5. Read the diff once more. Revert any change that doesn't make the code easier to read.
6. If one pattern showed up in three or more files, propose a Biome rule for it.
